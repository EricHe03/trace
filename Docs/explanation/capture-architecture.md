# Capture Architecture

This page explains how Trace's three capture paths work, how they interact, and why the design is split the way it is.

## The three capture paths

```
┌─────────────────────────────────────────────────────────────┐
│                        iOS Device                           │
│                                                             │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐  │

│         │                  │                   │           │
```

### Path 1 — System proxy (Proxy mode)

iOS allows an app to register as the system HTTP/HTTPS proxy. When Trace does this, other apps automatically route HTTP and HTTPS `CONNECT` tunnel requests through Trace's local MITM proxy server.

- Entry point: `TraceProxy/MITM/MITMProxyServer.swift`
- Engine: `TraceProxy/MITM/NIOMITMProxyEngine.swift`
- TLS termination: NIOSSL, with per-host certificates generated by `TraceSecurity`
- HTTP versions: HTTP/1.1 and HTTP/2 (via ALPN negotiation)

Not all apps use the system proxy. Apps that manage their own `URLSession` configuration, use third-party networking libraries, or explicitly disable proxying are invisible to this path.

### Path 2 — Packet tunnel (Full-tunnel mode)

The `TraceVPN` Network Extension creates a TUN virtual network interface. All IP traffic leaving the device flows through the TUN device first.

The embedded C library `hev-socks5-tunnel` (`ThirdParty/hev-socks5-tunnel/`) handles the TUN-to-SOCKS5 conversion. It maps each TCP connection and UDP flow from the TUN device to a SOCKS5 association on a local port, where `TraceVPN/Providers/LocalSocks5Server.swift` picks it up.

From the SOCKS5 layer, TCP flows can either:
- Be forwarded directly to the real destination (pass-through), or
- Be forwarded to the MITM proxy engine (hybrid TCP MITM mode), where HTTP/HTTPS interception proceeds as in path 1.

UDP flows are handled by `TraceVPN/Providers/UDPForwarder.swift`.

QUIC/HTTP3 flows arrive as UDP packets on port 443. Trace can either:
- Pass them through (they appear as opaque UDP flows), or
- Block them by dropping the packets, forcing the client to fall back to HTTP/2 over TCP.

### Path 3 — URLProtocol (Trace's own traffic)

Traffic that Trace generates itself (request replay, the request builder, diagnostics) takes a different path. Trace registers `Trace/NetworkInterceptor.swift` as a `URLProtocol` subclass that intercepts `URLSession` requests inside the Trace process.

This is intentionally separate from the NIO path because `URLProtocol` is the only Apple-sanctioned mechanism for intercepting traffic within an app's own process. The NIO MITM proxy handles external clients; URLProtocol handles Trace's internal client.

## gRPC metadata capture

When Trace intercepts HTTP/2 traffic, it automatically detects gRPC responses and extracts structured metadata from the HTTP/2 trailing HEADERS frame. Per the gRPC-over-HTTP/2 spec, the server sends a trailing HEADERS frame with `END_STREAM` set containing the status fields. AsyncHTTPClient merges these trailing headers into the final response headers, so the same extraction path handles both buffered and streaming captures.

Extracted fields stored in `NetworkRequest.GRPCMetadata`:

| Field | gRPC header | Notes |
|---|---|---|
| Status code | `grpc-status` | Integer; 0 = OK. See [gRPC status codes](https://grpc.github.io/grpc/core/md_doc_statuscodes.html) |
| Status message | `grpc-message` | Percent-decoded per gRPC spec §2.4 |
| Encoding | `grpc-encoding` | E.g. `identity`, `gzip` |
| Message count | _(computed)_ | Number of length-prefixed gRPC frames in the body buffer |

If no `grpc-status` header is present the response is treated as plain HTTP/2 and no gRPC metadata is stored.

**Implementation:** `TraceProxy/MITM/GRPCTrailerExtractor.swift` — `extract(from:)` and `countMessages(in:)`.

## Shared NIO runtime

All three targets that do networking share a single event loop group and AsyncHTTPClient instance, managed by `TraceCore/Networking/NIORuntime.swift`. This avoids redundant thread pools and ensures orderly teardown.

See [SwiftNIO Behavior Parity Contract](../SwiftNIO-Behavior-Parity-Contract.md) before modifying `NIORuntime.swift`.

## Shared storage

All three targets (app, VPN extension, widget) read and write a single GRDB-backed SQLite database in the App Group container. GRDB provides serialized write access; multiple readers are allowed concurrently.

Captured request and response data, connection events, and DNS records are all written to this database. The main app reads from it to populate the Network tab in real time.

## Swift 6 concurrency

The project targets Swift 6 strict concurrency. All types that cross actor boundaries must conform to `Sendable`. The NIO channel handlers and MITM pipeline components are carefully annotated to avoid data races. Introducing `nonisolated(unsafe)` or removing `Sendable` conformances without understanding the existing isolation model will likely introduce races.
